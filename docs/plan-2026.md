## Правила ведения файла

| Отметка | Значение |
|---|---|
| `[ ]` | не начато |
| `[~]` | в работе (указать, кто/когда начал) |
| `[x]` | сделано, проверено командой из задачи |
| `[—]` | решено не делать (причина в «Решениях») |

После каждой закрытой задачи:

1. отметить чек-бокс (`[x]`) и, если есть, вложенные пункты;
2. добавить строку в **«Журнал работ»**: дата, задача, что сделано, чем проверено;
3. если решение меняет архитектуру — запись в **«Решения»** с датой и причиной;
4. обновить поле **«Текущая фаза / Ближайшая задача»** в шапке.

Не отмечать задачу сделанной без прогона её команды проверки. «Код написан» ≠ «сделано».

## 1. Контекст: почему план такой

Короткая выжимка исследования от 20.11.2026. Нужна, чтобы следующий агент понимал
причину задач, а не выполнял их механически.

**Что изменилось в фильтрации:**

1. **Заморозка по объёму (главное).** ТСПУ перестала искать сигнатуры: TCP-соединение
   живёт, TLS проходит, а после ~25 пакетов в одну сторону (≈4,8 КБ при мелких пакетах,
   до 33 КБ при полных) пакеты просто перестают идти. RST не приходит — клиент ждёт
   таймаут. На мобильных порог ниже (~8 пакетов). Порог задан **в пакетах, а не в байтах**.
2. **Обрыв по ASN назначения.** Hetzner, DigitalOcean, Vultr, Scaleway, M247, OVH
   режутся целиком. UDP при этом не затронут (AmneziaWG работал, когда TCP зависал).
3. **Бан IP и подсетей после распознавания протокола** — через 25 ч – 2 суток; до
   5 000 адресов из 30 000 на один хостинг. Возврат примерно через две недели.
4. **Поведенческий анализ (гипотеза, один источник).** Совпадение трёх признаков:
   «подозрительный» ASN + >3 параллельных TLS-хендшейка к одному SNI + Chrome-uTLS →
   заморозка ~120 с; смена отпечатка под нагрузкой → штраф до 600 с.
5. **Белые списки по IP-префиксам** у мобильных операторов (~900 ресурсов, разные у
   разных операторов и регионов).
6. **Национальный DNS (НСДИ).** Домен удаляют из НСДИ → NXDOMAIN. Это не ТСПУ.

**Что из этого следует для проекта:**

- бесплатные списки узлов живут на «расходных» ASN — модель «собрать и подключиться»
  упирается в потолок, это не лечится парсингом;
- проверка живости должна мерить **объём**, а не задержку: сейчас `TestUrl`
  (`https://www.youtube.com/`, `HttpCompletionOption.ResponseHeadersRead`) даёт только RTT,
  и узел, проходящий 5 КБ, помечается рабочим;
- единственный консенсус сообщества — **цепочка «мост в РФ → зарубежный выход»**;
- **xHTTP packet-up** решает и freeze по объёму, и «залп хендшейков», но **sing-box его
  не поддерживает** (транспорты: HTTP, WS, QUIC, gRPC, HTTPUpgrade) — отсюда фаза 6;
- фрагментация TLS-записей (`tls.record_fragment`) уменьшает байты на пакет и
  **приближает** заморозку: полезна для рукопожатия, вредна для данных.

## 12. Сквозные требования (в каждой фазе)

1. **Сборка и тесты.** `dotnet build` обязателен; после изменений разбора — `parsers`;
   после изменений конфига — `checkconfigs`; перед сборкой закрыть `VieNLink.exe`.
2. **Self-test как приёмка.** Каждая фича получает команду (`volume`, `profile`, `chain`,
   `tuic`, `xhttp`). Без команды фича не сделана.
3. **Кэш и подпись конфига.** Новые поля → `CachedNode` + `SchemaVersions` + миграция в
   `SettingsUpgrade`; всё, что влияет на конфиг — в `_loadedSignature`.
4. **Стиль.** Комментарии, логи и UI — по-русски; 4 пробела; `namespace VieNLink`;
   без NuGet-пакетов.
5. **Гипотезы помечать.** Числа из одного источника (120 с, >3 хендшейка, TTL-пороги) —
   в комментарии как наблюдение; в UI показывать **свой** замер.
6. **Регрессия Cloudflare.** Любая новая техника DPI проверяется на «не сломать обычные сайты».

## 16. Как продолжать (обязательно для следующего агента)

**Порядок чтения:** `AGENTS.md` → этот файл → `docs/VERSIONING.md`.
Если задача про Android — сначала `docs/android-design.md`, там матрица возможностей
платформы, развилка ядра и список классов.

**Что делать первым:**

1. Задача **0.2** закрыта 21.11.2026 (74 проверки парсеров, 22 варианта конфига, Windows
   собирается без предупреждений). Следующая по плану — **1.1** (измерение объёма).
2. Остаток **8.4**: тест VPN на втором операторе/устройстве; плитку владелец добавляет
   вручную (ColorOS не даёт сделать это с машины). `BOOT_COMPLETED`, «Лучший» в уведомлении
   и экран «О программе» проверены 21.11.2026.
3. Windows: задача **1.1** (измерение объёма) и остаток **4.1** (`wssize`, `hopbyhop`,
   `destopt`, `synack`, `rst`/`rstack`, дублирование SYN с MD5).
4. Правовые **0.4–0.5** закрыты 21.11.2026; после публикации репозитория — только
   обновить `docs/VERSIONING.md` (сейчас GitHub отдаёт 404, репозиторий ещё не публичный).

**Грабли, на которые уже наступали:**

- `NodeStatus` используется в `switch` (`SelfTest/Program.cs`, `ViewModels.cs`,
  `MainWindow.Nodes.cs`) — новое значение нужно добавить везде, иначе молчаливый `default`.
- Новые поля узла → `CachedNode` + `SchemaVersions.NodeCache` + миграция, иначе после
  перезапуска данные пропадут (или кэш прочитается неверно).
- Всё, что влияет на конфиг, обязано попасть в `_loadedSignature`, иначе смена настройки
  не пересоберёт конфиг и «не работает».
- sing-box не понимает BOM в JSON — конфиг писать только UTF-8 без BOM.
- `LinkParser.ApplyTransport` не имеет `default`: неизвестный транспорт = «тихий» голый TCP.
- sing-box **не** поддерживает xhttp — не пытаться собрать его конфиг с `type: xhttp`.
- Проверки через Clash API дают только задержку. Объём, RST и заморозку так не увидеть —
  нужен прямой замер через локальный порт.

**Чего не делать:**

- не начинать фазу 8 (Android) раньше контрольной точки фазы 3 — это отдельный продукт
  со своей UI-кодовой базой, и он не должен забирать ресурс у Windows-версии;
- не включать `multiplex` «для маскировки» — он тратит пакетный бюджет быстрее;
- не хардкодить чужие константы (120 с, >3 хендшейка) как факты;
- не тащить olcrtc/WebRTC и «данные через маркетплейсы» в продукт;
- не добавлять NuGet-пакеты;
- не переписывать архитектуру без записи в «Решениях».
