# План работ: VieNLink 2026–2027

Файл сокращён 22.11.2026: подробная история — в git и `CHANGELOG.md`, технические правила —
в `AGENTS.md`, состояние и следующий шаг — в `docs/handoff.md`. Здесь только план и краткий
журнал.

## 0. Текущее состояние (25.11.2026)

Версия **1.3.54**. Сейчас работаем только с Android: TUN-обход без сервера (OOB,
QUIC через релей с фейком), автоподбор стратегий под сеть/оператора, база подборок,
журнал по категориям и QUIC-ответы в «Данных обхода». Windows-клиент и релизы —
по мере необходимости, не в текущем фокусе.

## 1. Сделано

- Windows-клиент: подключение по сервисам, смена сервера, проверка в скрытом ядре, трей,
  виджет, автозапуск, обновление с зеркал, диагностика, профили удачных обходов.
- Android-клиент: VPN-служба с автопереключением, процесс `:probe` для проверки серверов,
  плитка, виджет, split-tunnel по приложениям, MTProto через RSS, автообновление APK.
- Общее ядро `VieNLink.Core` без Windows-зависимостей — путь к libXray при необходимости.
- Разбор ссылок и подписок (base64, Xray/sing-box JSON, Clash YAML), склейка дублей, кэш.
- Обходы DPI: TLS-фрагментация sing-box, свой движок WinDivert, TUN-обход без сервера.
- Android: журнал с фильтром по категориям (Обход · Проверки · MTProto · Обновления ·
  Ошибки · Всё) и QUIC-ответы (downlink) в «Данных обхода» (25.11.2026).
- Релизы: Windows ZIP + подписанный установщик, GitHub APK, магазинные APK/AAB.

    реализации обновить её и оставить отправку **только по кнопке**.

## 3. Решения (кратко; подробности — в AGENTS.md)

- **Чёрный список источников и негативный кэш серверов (25.11.2026).** Ручная блокировка
  источника — навсегда, авто — мягкая на 30 дней с ключами URL/репозиторий/семейство дат.
  Негативный кэш хранит провал ядра по полному `Id` (24/48 ч) и TCP-провал по `host:port`
  (6 ч); успех снимает запись. Это закрывает цикл «удалили — автопоиск добавил снова» и
  экономит повторные проверки одинаковых мёртвых ссылок. На ТВ интерфейс списка скрыт.
- **Журналы хранятся 72 часа (25.11.2026).** Категории одинаковые на ПК и Android
  (`AppLogCategories`), на ПК журнал читается из файла с фильтром; старые журналы,
  `core-stderr.log`, временные `runtime/*.json`, `rawcache` и `probe-*.json` удаляются
  при старте, раз в час записи и в фоновом обслуживании Android.

- **QUIC-фейк без raw-сокетов (25.11.2026).** TLS-фрагментация работает только по TCP,
  поэтому обход не мог тронуть QUIC (HTTP/3) — оставалось только блокировать UDP/443.
  Теперь форвардер принимает SOCKS5 `UDP ASSOCIATE`, а перед настоящим QUIC Initial
  отправляет фейковый Initial с безобидным SNI (шаблон zapret, TTL 8, 11 копий):
  байты настоящего пакета не правятся, root не нужен. Включается снятием галочки
  «Блокировать QUIC»; UDP/443 в конфиге идёт в outbound `fragment`, остальные UDP —
  напрямую. Ограничение: при блокировке по IP/сигнатуре (а не по SNI) не помогает.
- Проверочные домены и сортировка (24.11.2026): проверочный список отделён от целей
  десинка — `TlsHello.VerificationDomains` (13 доменов, без X/Twitter/Facebook/
  Instagram-CDN; `TargetDomains` остался для zapret/десинка), проверка стала быстрее.
  Задержка `DelayMs` на ПК теперь по универсальному адресу (Cloudflare), а не
  YouTube/Telegram — «самый быстрый для сервиса» стал осмысленным для «Универсального»
  и «Discord» (на Android `DelayMs` и так Cloudflare). На ПК Cloudflare стал основным
  признаком годности в базовой проверке (проверяется параллельно с YouTube/Telegram):
  новый сервер, открывающий только Cloudflare, больше не удаляется — как на Android.
  Android `PickForService` сортирует по задержке, а не по числу открытых доменов. ПК:
  стартовая перепроверка рабочих запускается при любых устаревших рабочих (не только
  при недоборе квоты), партия до 200, параллельность 24.
- Проверка сервера = HTTP-запрос через него, а не пинг; «рабочий» = сайт открылся.
- Проверка через поднятый прокси (health-check, проверка после подключения) — только повод
  переключиться; `Working`/`FailCount` меняет лишь прямая проверка в скрытом ядре. Адреса
  такой проверки — универсальный Cloudflare и сервис, который сервер уже открывал.
- Два правила доступности (23.11.2026): показ — `NodeAvailability.IsCountable` (рабочий,
  последняя удачная проверка прошла, подтверждённого провала не было, результат не старше
  `WorkingDeadAfterMinutes`), выбор для подключения — `NodeAvailability.IsUsable`
  (то же + проверка не старше `WorkingRecheckMinutes`). Счётчики в шапке не обнуляются
  по таймеру 5 минут — иначе при каждой перепроверке все значки падали в ноль, хотя
  рабочие серверы живы; уменьшает их только подтверждённый провал. Кнопка сервиса при
  отсутствии свежих проверяет тех же серверов скрытым ядром на месте — число на значке
  и результат нажатия не расходятся.
- Android: счётчики шапки обновляются по ходу партии — процесс `:probe` пишет готовые
  результаты в `probe-live.json`, основной процесс применяет их сразу (а не после партии).
- Android: список серверов живёт снимком (`NodeStore._snapshot`); UI читает его без замка,
  тяжёлую работу (разбор кэша, склейку источников, запись кэша) делает только фон.
- Ядро — внешний sing-box/libbox, ядро общее для ПК и Android; NuGet не добавляем.
- Обходы взаимоисключающие: сервер ↔ zapret ↔ свой WinDivert ↔ TUN-обход.
- Оценка «годится для видео» (23.11.2026): проба видео проверяет до 2 разных хостов
  googlevideo (локальный GGC провайдера часто режется по IP, другой узел может отдавать
  поток) и требует ≥64 КБ реального потока; после трёх пустых проверок видео больше не
  проверяется, автоподбор останавливается на первом подтверждённом видео. Если проверка
  врёт (браузер играет — curl получает 0), остаётся ручной выбор: список стратегий
  кликабельный, выбор сохраняется в `DesyncManual` и не подменяется профилем.
  Стратегия «Только QUIC-фейк» проверяется QUIC-рукопожатием (h3) и при успехе
  выключает блокировку QUIC. На проверенном провайдере QUIC заблокирован полностью,
  но видео **идёт по TCP со стратегией №2** (перемотка продолжилась, порт 443 к
  `178.176.143.237/238` открыт). Прямая проверка `videoplayback` из curl/.NET даёт 0
  из-за браузерной подписи/n-sig, поэтому проверяем **yt-dlp** с клиентом android:
  он скачивает реальные байты (629 172), и стратегия получает `VideoOk`. yt-dlp
  скачивается один раз в `%LOCALAPPDATA%\VieNLink`; рабочий профиль запоминается
  с Quality 100. UI: стратегии — кликабельные плашки, кнопки с градиентом/тенью,
  вкладки с цветными подчёркиваниями, шапка без дубля названия, фиксированное окно 980×680 с запоминанием позиции.
- GPL-3.0 обязательна из-за libbox; закрытая сборка возможна только на libXray.
- Две поставки Android: GitHub (самообновление) и магазинная (без `REQUEST_INSTALL_PACKAGES`).
- Адаптивный UI Android (24.11.2026): масштаб отступов считается не только по форм-фактору,
  но и по реальной ширине/высоте экрана (`DeviceProfile.WidthDp/HeightDp`, `IsCompact`,
  `IsShort`); системный «Размер текста» ограничен `Ui.FontLimit` (1.28 телефон, 1.12 ТВ).
  Тесные ряды шапки строятся на весах и многоточии, а не на фиксированных ширинах.
  Главная шапка должна помещаться целиком на 360×640dp: «Выход»+«Трафик» в одной строке,
  «СЕРВЕР ОТКРЫВАЕТ»+значки в одной строке, MTProto и «Добавить сервер» — один ряд.
  Отступы системных панелей — по `WindowInsets` (с откатом на высоты из ресурсов).
  Для проверки раскладки — AVD `vienlink-phone-320/360/411` и `vienlink-tablet-600`
  в `%LOCALAPPDATA%\android-sdk` (образ `system-images;android-36;google_apis;x86_64`).
- Адаптивный UI Windows (24.11.2026): размер окна подгоняется под рабочую область
  (`min(953, area.Width-24) × min(620, area.Height-24)`), желаемый — 980×680; счётчики шапки
  в `WrapPanel`, вкладки в горизонтальной прокрутке, ряды кнопок «Отсева» и TUN-обхода
  переносятся, нижняя строка — в двух колонках с многоточием. ПК не масштабируется целиком:
  при уменьшении окна страницы прокручиваются, а не обрезаются.
- Автоматика: `AutomationPaused` — общий выключатель, плюс отдельные флаги работ
  (`AutoDiscoverSources`, `AutoCollectServers`, `IdleTestEnabled`, `AutoMtProto`,
  `AutoUpdateCore`, `AutoCheckAppUpdates`). Каждый цикл сам проверяет свой флаг, поэтому
  включение одной работы не запускает остальные.
- Статистика источника: «Рабочих» считается по текущему списку (`NodeSourceStats`),
  «Всего» — уникальные Id за всё время (`TotalNodeCount` + `RegisteredNodeIds`), иначе
  повторный сбор одного и того же списка раздувал бы число.
- Отсев (`nodes-rejected.json`) пополняется только после завершения партии проверки
  (`RepartitionAndSaveAsync`): при откате «ни один сервер не открылся» статусы уже
  восстановлены, и рабочие серверы не остаются в отсеве. Подключение через прокси
  и health-check статус не меняют — только переключают.
- Повторные проверки (23.11.2026): после провала рабочего сервера — пауза
  `NodeLimits.WorkingRetryMinutes` (3 мин) по `TriedAtUtc`; успешная проверка
  (`FailCount = 0`) паузу снимает, ручная перепроверка её обходит. Провал сначала
  подтверждается отдельной проверкой после партии (`ConfirmFailedWorkingAsync`):
  Cloudflare/YouTube/Telegram; если сервер открыл хотя бы один адрес, провал не
  засчитывается. Рабочий сервер удаляется после `RemoveAfterFailures` (5), а не 3,
  и только если с последнего успеха прошло `WorkingDeadAfterMinutes` (60): «моргающий»
  VLESS/Reality-сервер в отсев не попадает. `WorkingRecheckMinutes` временно 1
  (проверка рабочих каждую минуту), вернуть 5.
  Если в партии проверено ≥3 ранее рабочих сервера и ни один не открылся, провалы
  не засчитываются (массовый сбой проверки/сети). Причина: на Android фон запускал
  4 партии за 2–3 минуты, и 6 живых серверов ушли в отсев после одной перегруженной
  партии (8 узлов × 6 адресов на мобильном канале).
- Счётчики в шапке ПК обновляются каждые 3 секунды (не раз в минуту): число рабочих
  и сервисов должно успевать за проверкой. Показываются «Серверы: N · рабочих: M», как
  на Android.
- ПК, запуск (23.11.2026): ранее рабочие серверы перепроверяются **до** обновления
  источников (как на Android). Раньше скачивание списков держало значки сервисов на нулях,
  хотя рабочие серверы в кэше уже были. Проверка и обновление списков идут параллельно.
- ПК, скорость фона (23.11.2026): параллельность 24 в простое / 16 при работе / 12 при
  подключении / 3 при обходе; партия при работе — половина настройки (до 60 серверов),
  перепроверка рабочих — до 40. Разгон параллельности после первых 40 серверов больше
  не требует 20 % живых: мёртвая партия — это таймауты, они не занимают канал, а на
  10 потоках 200 серверов проверялись минутами.
- Проверка «от источника» (24.11.2026): партия больше не набивается первыми серверами
  списка. `NodeFailover.TakeWithSourceCap` даёт источнику без рабочих серверов 3 слота,
  «среднему» — 6, источнику с подтверждённым выходом — до 10; `sourceScore` в сортировке
  стоит выше свежести. Оценка источника считается по проверенным серверам, а не по всем
  (у свежего большого списка выход иначе всегда «почти ноль»). `NodeSourceStats.BarrenSources`
  исключает из фоновых партий источники, где проверено ≥ 50 серверов и нет ни одного
  рабочего (ручная проверка и «Перепроверить всё» ограничение обходят).
- Каналы Telegram — теперь и серверы, не только MTProto (24.11.2026): `SourceKinds.IsServerSource`
  включает t.me-каналы в общий сбор серверов — публичные конфиг-каналы постят vless/vmess,
  а не только tg://proxy. Сайты/списки MTProto (`SourceKind.MtProto`) остаются только
  прокси. У каналов нет даты коммита на GitHub, поэтому фильтр свежести их пропускает
  (`GitHubSourceFreshness` не удаляет канал); при заблокированном t.me канал в сборке
  серверов падает с подсказкой, не роняя остальные.
- Устойчивость и экономия сбора (24.11.2026): кэш дат публикации GitHub на диске
  (`freshness.json` — после перезапуска не жечь квоту API заново), условные GET по ETag
  с кэшем сырого ответа (`raw-etags.json` + `rawcache/` — при 304 список пересобирается
  из кэша без скачивания, поэтому серверы источника не пропадают из пересборки), зеркала
  `ghfast.top`/`gh-proxy.com` для raw-контента (раньше зеркала были только у API-дат).
  Добавлен разбор `tuic://` (TUIC v5 — sing-box поддерживает); `ssr://` сознательно не
  добавляем: sing-box не умеет ShadowsocksR, такие серверы были бы мёртвым грузом.
- Ротация «бесплодных» источников (24.11.2026): давний серверный источник, отдавший
  ≥ `NodeLimits.BarrenMinNodes` (200) серверов и не давший ни одного рабочего
  (`TotalWorkingNodeCount == 0`), отключается после `BarrenDisableAfter` (3 дня с момента
  `FirstSeenUtc`) и удаляется через `BarrenRemoveAfter` (7 дней с отключения) — на его
  место автопоиск подбирает новый. Личные подписки и MTProto-источники не трогаются.
  `FirstSeenUtc` ставится при загрузке списка (разовая миграция), `BarrenSinceUtc` —
  метка карантина. Отключение/удаление возвращаются из `CollectAsync`
  (`SourcesToDisable`/`SourcesToRemove`), применить их — задача UI.
- Контент-дедуп источников (24.11.2026): `FetchOutcome.ContentHash` (SHA-256 сырого
  текста) + `NodeSourceStats.DedupMirrors` — источники с одинаковым текстом считаются
  зеркалами одного списка; оставляют лучший (мой → доверенный → больше рабочих →
  раньше появился), автоподобранные зеркала удаляются (`SourcesToRemove`), остальные
  просто не дублируют узлы. Убирает мусор от репозиториев, копирующих одни и те же списки.
- Telegram-каналы серверов через RSS (24.11.2026): сбор серверов из t.me-каналов теперь
  повторяет путь MTProto — сначала прямой t.me, при неудаче или пустом ответе — RSS-зеркала
  (`NodeSourceService.TelegramRssMirrors`, общие с MTProto). `FetchAsync` разложен на
  `FetchTelegramAsync` (прямой + RSS) и `ParseText` (общий разбор). При заблокированном
  t.me конфиг-каналы больше не дают ноль.
- Бюджет обращений к GitHub API (24.11.2026): `GitHubSourceFreshness.ApiBudget`
  (`MaximumApiRequests = 30`) — на один сбор не больше 30 проверок дат; источники сверх
  лимита собираются без проверки даты (как при недоступном API), а не пропускаются.
  Защищает от «веера» запросов на холодном старте и после истечения кэша дат (1 ч).
- «Переехал ≠ умер» (24.11.2026): источник, у которого не определяется дата публикации
  (API отвечает, но даты нет), больше не удаляется сразу — уходит в карантин
  (`SourceDefinition.QuarantineSinceUtc`, отключение через `SourcesToDisable`), а удаляется
  `RotateQuarantinedSources` только после `QuarantineRemoveAfter` (7 дней). Если дата
  снова определилась, карантин снимается. Недоступный API (`ApiReached=false`) карантин
  не вызывает — это не вина источника.
- Автопоиск публичных сайтов оживлён (24.11.2026): `DiscoverWebAsync` снова вызывается из
  `DiscoverAsync`; дата публикации берётся из адреса статьи/файла
  (`SourceDiscoveryService.ExtractPublishedDate` — «2026-11-19»/«20261119») и ставится в
  `LastPublishedUtc`+`IsTrusted`. Свежесть таких не-GitHub источников считается по этой дате
  (`GitHubSourceFreshness`), `LoadSources` их не удаляет. Флаг `includeWeb=false` выключает
  обход сайтов на ТВ.
- GitLab и Gitee (24.11.2026): `SourceLocation.Host` различает github/gitlab/gitee,
  `TryGetLocation` разбирает raw-ссылки `gitlab.com/…/-/raw/…` и `gitee.com/…/raw/…`,
  свежесть идёт через их API (GitLab `committed_date`/`last_activity_at`, Gitee
  `commit.committer.date`/`updated_at`) без GitHub-зеркал. Автопоиск тоже ищет по

## 5. Как продолжать

1. Прочитать `AGENTS.md`, затем `docs/handoff.md`.
2. Проверить сборку: `dotnet build VieNLink\VieNLink.csproj` и Android отдельным SDK
   (команды в `AGENTS.md`).
3. Прогнать нужный режим `VieNLink.SelfTest` для своей задачи.
4. После задачи: `CHANGELOG.md`, запись в журнал выше, чек-бокс в разделе «Дальше»,
   обновить `docs/handoff.md` и версию в `build/Version.props` при релизе.
