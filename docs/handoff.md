## «Сервер рабочий, а сервисы не работают» (27.11.2026)

- **Android.** На телефоне (1.3.58, Android 16, строгий Private DNS `dns.google`) сервер
  был живой (Clash API: Cloudflare 2,3 с, YouTube 1,3 с), но в VPN не резолвились имена:
  `ping cp.cloudflare.com` → `unknown host`, YouTube не открывал соединений, VPN-сеть
  висела с `PrivateDnsBroken`. Выключение Private DNS сразу восстановило резолв, YouTube
  загрузился; включение обратно — Android перепроверил DoT через туннель, и всё работало.
  Причина: Android проверяет частный DNS один раз при создании VPN-сети; проверка VieNLink
  идёт в `:probe` вне VPN и сломанный DNS не видит.
- **Что сделано:** `TunnelService.StartPrivateDnsMonitor` — раз в 90 с смотрит
  `IsPrivateDnsActive` + `ValidatedPrivateDnsAddresses` (строка `LinkProperties`,
  Android 14+), при неподтверждённом строгом DNS и живом выбранном сервере перезапускает
  службу (новая VPN-сеть → новая проверка DoT). Не чаще 2 раз за сессию и раза в 10 минут;
  `_privateDnsSelfRestart` не сбрасывает счётчик при своём же перезапуске.
- **ПК.** Сервер был живой (`t.me` через узел 436 мс, YouTube 243 мс), но включён режим
  «только сайты из списка», а в списке были лишь `www.youtube.com` и `discord.com`:
  Telegram и видео-CDН YouTube шли `direct` и не открывались. Кнопки сервисов теперь
  добавляют полный набор доменов сервиса в список (YouTube — `YouTubeProxyDomains`,
  Telegram — t.me/telegram.org/CDN, Discord — discordapp/CDN); `ProbeUrlsForService`
  для YouTube проверяет ещё `redirector.googlevideo.com`.
- **Сборка:** `dotnet build VieNLink.slnx` (Android — через локальный SDK) — 0 ошибок;
  `SelfTest parsers`, `checkconfigs`, `statuslogic` — в порядке.
- **Опубликовано 27.11.2026:** `v1.3.59-beta` (Windows: `setup.exe` 97 934 968 байт,
  SHA-256 `1F6E3590…`; ZIP 106 507 680, SHA-256 `535410C8…`; `SHA256SUMS.txt`) и
  `v1.3.59-android` (`VieNLink-1.3.59-phone.apk` 45 254 305, versionCode 10359,
  SHA-256 `1126BF5A…`, + `.apk.sha256`), оба pre-release, теги на коммите `bd90729`.
  ТВ не пересобирали (ритм — раз в ~5 патчей), магазинные сборки не собираются (заморозка).
- **Дальше:** если тема повторится — проверить на телефоне `dumpsys connectivity`
  (`InterfaceName: tun0`, `ValidatedPrivateDnsAddresses`), а на ПК —
  `runtime\sing-box-config.json` (`route.rules`: какие домены идут в `proxy`, а какие
  в `direct`). Telegram Desktop на ПК системный прокси не использует: нужен TUN-режим
  или собственный прокси `127.0.0.1:20800`.

## 1.3.58 — правки по списку владельца, замеры и релиз (26.11.2026)

**Опубликовано 26.11.2026:** `v1.3.58-beta` (Windows: `setup.exe` 93,4 МБ,
SHA-256 `D86CCF19…`, + `SHA256SUMS.txt`) и `v1.3.58-android`
(`VieNLink-1.3.58-phone.apk` 43,2 МБ, SHA-256 `65EC50C4…`, + `.apk.sha256`),
оба pre-release, ссылки проверены head-запросами — HTTP 200 и правильные размеры
(97 935 840 и 45 250 209 байт). Исходники запушены — коммит `8d953e7` (ветка `main`),
теги на нём. ТВ не пересобирали — по ритму раз в ~5 патчей (последняя 1.3.55).
Версия 1.3.57 собиралась локально и в релиз не попала.

- **Порядок в `ProbeClient`:** прошлый `:probe` гасится и ожидается до 3 с, затем удаляются
  `probe-results/progress/live`. Результаты применяются по `Id` к актуальному снимку
  (`NodeStore.IndexById`), поэтому `Merge` во время партии больше не «съедает» успехи.
  `ApplyPendingResults` применяет файл только свежее 60 минут (`SavedAtUtc`; старые файлы —
  по времени файла).
- **Выбор сервера:** `MainActivity.StartForService` вызывает `NodeStore.Select(node)` до
  ветвления warm/cold. `NodeStore.Select` пишет `selected-node.json` в фоне (очередь
  pending/running), `PersistenceSuppressed` отключает запись на время автопроверки отсева.
- **Ручной сервер:** `NodeStore.AddManual` ставит `IsMine = true`.
- **Отсев:** `RejectedActivity` возвращает сервер только при реальных байтах
  (`_downBytes + _upBytes > 0`, поток Clash слушается всегда), `RejectedBootCheckService` —
  партия 4 сервера, запрос через туннель (`ClashApiClient.TestDelayAsync`), `_done`
  ставится после проверок, `selected-node.json` не трогается.
- **Оптимизации:** `NetworkProbe` — один `HttpClient` на направление, `LookupExitAsync`
  отдаёт кэш и не ходит в сеть до его истечения (5 мин), клиенты сбрасываются в
  `Invalidate`; шапка Android (`SetText`/`SetTextColor`/`SetVisibility`) и плашка обхода
  обновляются только при изменении; `ProbeService` пишет прогресс/live не чаще раза в
  секунду, `ProbeClient` читает файл прогресса только при изменении метки времени.
- **ПК «Источники»:** колонка «Пинг» = `NodeSourceStats.MedianDelayBySource` (медиана по
  проверенным, минимум 3 замера). `NodeLimits.Trim` при обрезке до лимита ставит серверы
  источников с медианой ≥1500 мс после остальных (`TrimBadSourceMedianMs`), неизвестная
  медиана не наказывается. Проверено скриншотом: в колонке 45 / 92 / 2243 мс.
- **Тексты:** подсказка авто-перепроверки отсева на ПК — «раз в 6 часов, только записи, не
  проверявшиеся дольше 6 часов»; комментарии в `MainWindow.IdleTest.cs` приведены к факту.
- **SelfTest:** ожидания `statuslogic` обновлены под правило «непроверенный получает второй
  шанс» (`NodeHealth.UnverifiedFailures = 2`); добавлены проверки медианы источника и
  обрезки списка по плохой медиане.
- **Сборки:** APK `release\VieNLink-1.3.58-phone.apk` (43,2 МБ, SHA-256
  `65EC50C4EFC171F2F21C26E18FD522AC6490C174603B08547F5D99E569D76A95`) установлен на
  RMX5120; `release\VieNLink-1.3.58-setup.exe` (93,4 МБ) установлен на ПК (1.3.58-beta),
  приложение запускается, системный прокси после проверок выключен.
- **Android: подбор и QUIC на главном экране.** В карточке «Обход блокировок без сервера»
  рядом с «Использовать обход» — кнопка «Подобрать стратегию» (быстрый перебор; пока идёт —
  «Остановить подбор») и галочка «Блокировать QUIC (UDP/443)» с короткой подсказкой, что
  пробовать при проблемах с видео. Логика перебора вынесена в `BypassAutotune` и общая
  с экраном TUN (там остался и подробный «Подобрать лучшую»). Проверено на RMX5120:
  кнопка показывает ход («Страница YouTube: первая рабочая «OOB» — 2/3 … · 93 КБ/с»),
  отмена возвращает «Подбор остановлен», галочка переключается и возвращается к пресету
  сети (для Wi-Fi «Lena11» — снята, QUIC через релей).
- **ПК: действия подключения — под шапкой и компактнее.** «Сменить сервер», «Поделиться»,
  «Отключить» (и «Отменить» во время операции) вынесены из шапки в отдельную полосу под
  ней, значки 13 px, шрифт 11,5, отступы 9,3. В шапке остались состояние подключения
  и карточка сервера. Проверено скриншотом подключённого состояния.
- **ПК: показатели сверены с кэшем.** 4895 = 75 рабочих + 4820 непроверенных; щит 52 —
  ровно быстрые доступные из 60 (медленнее 2000 мс отброшены), значки 35/30/37/48 — те же
  быстрые по сервисам (совпали до единицы). Строка «Проверено 15 из 15: рабочих 13» была
  ходом партии — теперь «Партия: 15 из 15 · открыли адрес 13», после партии — «Фон: партия
  15 · открыли адрес 13 · доступных в шапке 52». На вкладке «Серверы» «свежих» больше не
  может быть больше «доступных» («из них свежих» считается по показанным).
- **Автоповорот на телефоне — не приложение.** Проверено на RMX5120: `accelerometer_rotation`
  приложение не пишет (в коде нет обращений к `Settings.System`); запуск с иконки при
  выключенном системном автоповороте оставляет его выключенным. `requestedOrientation`
  у `MainActivity` — `SCREEN_ORIENTATION_PORTRAIT` (`sw360dp`, `w360dp h785dp`), при
  принудительном системном ландшафте экран остался `ROTATION_0`. Планшет по дизайну
  получает `FullSensor`, ТВ — `Landscape`. Системный тумблер автоповорота живёт своей
  жизнью (его включает ОС/другие приложения; даже `monkey` в проверке включал его).
  **Добавлена диагностика и страховка:** ориентация повторно запрашивается в `OnResume`;
  в журнал пишется значение `accelerometer_rotation` при старте приложения, при открытии
  системного установщика APK, после установки обновления и при изменении настройки на ходу
  (`Поворот (...)`). По этим строкам после следующего обновления видно, на каком шаге
  системный тумблер включился — приложение его не меняет.

Ограничения замеров:
- **ПК TUN-обход не снят:** запуск требует прав администратора и интерактивного UAC
  (`ConsentPromptBehaviorAdmin = 5`, окно на защищённом рабочем столе). Вместо него снят
  ближайший доступный режим — видео через прокси-сервер (системный прокси), он же нагружает
  `sing-box.exe`.
- **`dumpsys netstats` по UID не обновился** за время сессии (история `bucketDuration=7200`
  и редкие флеши): дельты по UID = 0, поэтому трафик по режимам считан по
  `/proc/net/dev` (`wlan0`, устройство целиком, без разбивки по приложениям).
- **Батарея:** оценка `batterystats` по UID обновляется редко; за 60 с дельта 0, накопленная
  оценка за сессию — 43,7 → 45,6 мА·ч (включает прежние запуски того же UID).
- Запись на диск ПК (10–16 МБ/мин при проверке) — это кэш `nodes-working.json` и журналы;
  отдельного троттлинга на ПК в этот заход не делали (в списке не было).

## База параметров обхода по операторам (25.11.2026)

- **Зачем:** собрать на устройствах проверенные параметры обхода под конкретного оператора
  и потом зашить их в сборку, чтобы у новых пользователей эти параметры применялись сразу.
- **Локальная база:** `%LOCALAPPDATA%\VieNLink\provider-presets.json` (Android — каталог
  данных приложения). Схема: `version`, `updatedUtc`, `presets[]` — на запись
  `key` («cell:&lt;MCCMNC&gt;:&lt;оператор&gt;»), `page`, `video`, `blockQuic`,
  `source` (`auto`/`manual`), `successes`, `lastSuccessUtc`. Читается с кэшем по
  времени изменения файла (экран обхода спрашивает пресеты каждые 2 с).
- **Зашитая база:** `VieNLink.Core/Assets/provider-presets.json` (встроенный ресурс,
  сейчас пустая). 25.11.2026 добавлен промежуточный слой — **обновляемая база**: тот же
  файл читается из ветки `main` репозитория (`ProviderPresetStore.RemoteUrl`) раз в сутки
  и при открытии экрана TUN, через зеркала GitHub; кэш — `provider-presets-remote.json`.
  Поэтому пополнять базу теперь можно правкой файла в репозитории, без новой версии APK.
  Порядок: своё устройство → обновляемая база → зашитая.
- **Когда пишется:** автоподбор, подтвердивший страницу и превью (`Strong`), вызывает
  `ProviderPresetStore.RecordSuccess` — параметры обновляются, счётчик растёт. Запуск
  «Включить TUN-обход» вручную пишет `RecordChoice` (`source=manual`): автоподбор такие
  записи не перезаписывает, только увеличивает счётчик. Сеть не определена — ключ пустой,
  запись не делается.
- **Порядок применения:** пресет этой сети → база по операторам (своё устройство, затем
  обновляемая из репозитория, затем зашитая) → пресет типа сети → общая стратегия.
  QUIC (`blockQuic`) тоже стал параметром сети:
  галочка на экране TUN сохраняется для текущей сети/оператора, а `BuildTunBypass` берёт
  `NetworkPresets.GetBlockQuic`. Автоподбор проверяет известный пресет сети **первым**,
  затем OOB и «Разрез TLS-записей» — знакомая рабочая стратегия не теряется в конце очереди.
- **Экспорт:** на экране TUN кнопка «Поделиться подборками под операторов» — отдаёт JSON
  через «Поделиться» и пишет его в журнал (тег `presets`). В экспорт попадают **только
  мобильные операторы**: Wi-Fi SSID — личные данные и не выгружаются, в зашитой базе их
  тоже нет.
- **Полное логирование:** при открытии экрана, старте обхода и автоподборе в журнал идёт
  снимок сети: `Сеть: мобильная сеть · МТС · ключ «cell:25001:МТС» · сети: CELLULAR
  VALIDATED, VPN (пропущен) · страница Oob (база операторов (зашитая)) · видео как для
  страниц (...) · QUIC блокируется (локальный пресет сети)`. Каждый шаг автоподбора
  (`Страница YouTube · 3/25: «OOB» — проверяю…`), смена видео-стратегии и галочки QUIC
  тоже попадают в журнал.
- **Проверка:** `SelfTest providerpresets` — 8 проверок (подтверждение, ручной выбор,
  приоритеты, экспорт без SSID, зашитая база) — всё в порядке.

## Пресеты обхода: на каждого оператора и Wi-Fi отдельно (25.11.2026)

- **Было:** два пресета — Wi-Fi и мобильная сеть; на новой сети/операторе стратегия
  сбрасывалась в OOB, хотя пользователь уже подобрал рабочую на другом.
- **Стало (`NetworkPresets`):** ключ конкретной сети — `wifi:<SSID>` или
  `cell:<MCCMNC>:<оператор>` (например, `cell:25001:МТС`), хранится в
  `android-settings.json` → `BypassPresets`. Для новой сети порядок: пресет сети → пресет
  типа (старые поля `TunBypassStrategyWifi/Mobile`) → последняя использованная
  (`TunBypassStrategy`). Пустое видео в пресете = «как для страниц».
- **Определение сети:** при поднятом VPN активная сеть — сам VPN, и Android помечает её
  `CELLULAR|VPN`; поэтому перебираем все сети, пропускаем VPN и IMS без INTERNET.
  Валидированная сеть приоритетнее (Wi-Fi без интернета + LTE → мобильная). Если физической
  сети нет, ключ пустой и **пресет не пишется** (раньше по умолчанию было Wi-Fi и стратегия
  попадала в чужой пресет).
- **Проверено на устройстве (25.11.2026):** Wi-Fi выключен, в `dumpsys connectivity` одна
  физическая сеть `MOBILE[LTE]` (VALIDATED, Private DNS `dns.google`), VPN-сеть
  `CELLULAR|VPN` с `UnderlyingNetworks:[1122]` — детектор обязан вернуть «мобильная сеть».
  SSID Wi-Fi читается только с разрешением на геолокацию; без него все Wi-Fi идут под
  общим ключом `wifi` (это ограничение Android 10+, не баг).
- **Видно в интерфейсе и журнале:** на экране TUN — «Стратегия фрагментации ·
  мобильная сеть · <оператор>»; при открытии экрана и при запуске обхода в журнал
  пишется `Сеть: <метка> · пресет «<ключ>»: страница X, видео Y`. Если обход уже
  работает, экран показывает выбранной реально запущенную стратегию (`ForwarderHost.Mode`).
- **Проверка:** сборка Android — см. результат ниже.

## Что сработало на телефоне: LTE, OOB, QUIC разрешён (25.11.2026)

Зафиксировано по живому логу (`logcat` + `media_session`) на realme RMX5120, Android 16,
сборка **1.3.52 (10352)**.

- **Сеть:** мобильная (Wi-Fi выключен: `cmd wifi status` → `Wifi is disabled`), Private DNS
  `dns.google` (DoT) — без него на этом операторе `youtube.com` не резолвится.
- **Оператор:** Tele2 («t2 Black») — приложение определило как `мобильная сеть · t2 Black`;
  ключ пресета `cell:25020:t2 Black` (MCCMNC 25020).
- **Стратегия TUN-обхода:** **OOB (срочный байт)** — в журнале у всех TLS-соединений
  `первые … байт → OOB на позиции …`; отдельная видео-стратегия не задана (как для страниц).
- **QUIC разрешён** (галочка «Блокировать QUIC» снята): sing-box пускал UDP/443 напрямую,
  YouTube тянул видео по QUIC (`router: sniffed packet protocol: quic, domain:
  rr3---sn-gvnuxaxjvh-axqd.googlevideo.com, client: quic-go`).
- **Видео действительно играло:** `media_session` — `PlaybackState position=1256037`
  (20:56), ролик SHIMOROSHOW «GTA 6 — ГРАБЛЮ ДОМА БОГАТЫХ…»; превью шли
  (`видео i.ytimg.com: 30580 байт получено`).
- **Повторено на тестовой сборке той же версии (03:0x, `com.vienlink.app.test`):** быстрый
  подбор (`Первая рабочая`) с первой же стратегии выбрал **OOB — 3/3 (страница ✓, превью ✓,
  API ✓) · 80 КБ/с**, после чего обход поднялся и **картинки и видео работают** — при этом
  в тестовой сборке QUIC **блокирован** (галочка стоит), то есть видео шло по TCP через OOB.
- **Часть видео-хостов при этом падает — это норма:** в QoE-логе YouTube
  `rr3---sn-gvnuxaxjvh-axqd.googlevideo.com` (`net.connect`, `cerrcode.-7`) и
  `r4---sn-aj5goc-5j.googlevideo.com` (`connecttimeout`); плеер переключается на SABR и
  другие узлы, воспроизведение продолжается. Один упавший `rr*` ≠ «видео не работает».
- **Найден и исправлен баг пробы видео:** старая ссылка `videoplayback?id=…&itag=18` без
  подписи отдаёт ~5 КБ HTML, поэтому проба писала `0 байт`, хотя видео играло. Теперь проба
  берёт свежую подписанную ссылку со страницы `watch?v=jNQXAC9IVRw` (regex по
  `"url":"https:\/\/rr…videoplayback…"`, кэш 15 мин), принимает `video/*`, `audio/*` и
  `application/octet-stream`, порог 64 КБ и замер скорости 3 с.
- **Wi-Fi (проверено 25.11.2026, тестовая сборка):** с **заблокированным QUIC** видео не
  идёт — `rr*` отдают 0 байт по TCP (SNI-блок). С **разрешённым QUIC через релей** всё
  работает: в журнале `QUIC: UDP-ассоциация №…` и `QUIC: фейк Initial ×11 (TTL 8)`,
  форвардер насчитал 283 соединения / 17 разрезано / 10 QUIC-сессий / 88 фейков, а карточка
  показала `Видео шло: по QUIC через релей (TCP-потока от медиасервера нет), сессий 10`.
  Отсюда и «раньше по Wi-Fi видео грузилось» — оно шло по QUIC, TCP-стратегия на него не влияла.
  Рабочая связка для Wi-Fi: **OOB для TCP + QUIC разрешён (релей с фейком)**.
  **Подтверждено пользователем 25.11.2026:** «заработало и на Wi-Fi».
- **YouTube может застрять после смены режима (25.11.2026):** туннель при этом жив
  (в карточке — 148 соединений, 97 QUIC-сессий, 583 фейка, «Видео: по QUIC через релей»),
  но приложение YouTube держит старую сессию/кэш и не начинает воспроизведение.
  Помогает перезапуск приложения YouTube (не обхода). На 1.3.54: не перезапускать туннель,
  пока идёт видео, и показывать QUIC-ответы (downlink) в «Данных обхода».
- **Важно для новой сборки:** в 1.3.52 снятая галочка означала «QUIC напрямую». С UDP-релеем
  та же галочка означает «QUIC через форвардер с фейковым Initial». Если с фейком станет хуже —
  верните галочку (TCP) или проверьте без фейка: это единственное отличие от записанной
  рабочей связки.

## Подбор стратегии: честные проверки и отмена (25.11.2026)

- **Симптом (устройство, 1.3.52):** подбор объявлял стратегию рабочей, когда грузилась
  только картинка/лента, а видео не играло. В живом логе: `i.ytimg.com: 0 байт` при
  «страница открылась», видео шло по QUIC к `rr3---…googlevideo.com` и часть узлов
  отваливалась по таймауту. То есть проверка по HTML/коду ответа ничего не говорила о видео.
- **Проверки ужесточены (`StrategyAutotune`):**
  - страница: `www.youtube.com` — только 200 + `text/html` + ≥2 КБ тела; превью
    `i.ytimg.com/…jpg` — 200 + `image/*` + ≥4 КБ; API — любой ответ < 500 (слабый сигнал);
  - стратегия «сильная» только если пришли байты и страницы, и превью, — иначе подбор
    идёт дальше и в итоге честно пишет «страница открывается, превью нет»;
  - видео: redirector → rr*-узел, успех только при 200, финальном хосте `googlevideo.com`,
    типе `video/*` и **≥64 КБ** потока (прежние 4 КБ проходили даже при заморозке ТСПУ);
  - видео-пресет сохраняется **только** по подтверждённым байтам; раньше при неудаче он

## TUN-обход: UDP-релей и фейковый QUIC Initial (25.11.2026)

- **Что сделано:** SOCKS5-форвардер (`TlsFragmentForwarder`) теперь принимает
  `UDP ASSOCIATE` (команда 3) и релеит QUIC. Перед первым настоящим QUIC Initial
  к назначению он отправляет 11 копий фейкового Initial с безобидным SNI
  (`www.google.com`, шаблон zapret `quic_initial_www_google_com.bin`, встроен в
  `VieNLink.Core/Assets`, 1200 байт) с TTL 8; настоящее соединение идёт следом.
  Дедупликация — 10 с на пару «локальный порт + назначение», счётчики
  `UdpAssociations`/`FakeQuicPackets` видны в статусе экрана «Обход» на Android.
- **Конфиг:** при снятой галочке «Блокировать QUIC» `BuildTunBypass` маршрутизирует
  UDP/443 в outbound `fragment` (форвардер) вместо `direct`; с галочкой — прежний
  `reject`. Другие UDP-порты идут напрямую, как раньше.
- **Почему без raw-сокетов:** фейк — это отдельная датаграмма с тем же адресом
  назначения и малым TTL, байты настоящего пакета не правятся, root не нужен.
  Ограничение то же, что у zapret: если провайдер режет по IP/по сигнатуре, а не по
  SNI, фейк не поможет — нужен сервер.
- **Проверка:** `dotnet run --project VieNLink.SelfTest -- forwarderudp` — локальный
  UDP-эхо-сервер, SOCKS5 UDP ASSOCIATE, настоящий Initial 1300 байт, 11 фейков,
  ответ клиенту, дедупликация и пропуск коротких датаграмм (13 проверок).
  `forwarderudpvia` — то же через настоящий `sing-box` (socks inbound → socks outbound):
  цепочка «sing-box → форвардер → эхо» работает, фейк уходит, ответ возвращается.
  `forwarder`, `forwardertls`, `checkconfigs`, `statuslogic`, `desync` — в порядке;
  сборка ПК и Android — 0 ошибок.

  `QUIC: фейк Initial ×11`. Если видео по-прежнему 0 байт — это IP-блок, нужен сервер.

  в лог не попадал. Правильно: проверять воспроизведение в приложении YouTube (`media_session`)
  или качать реальный `videoplayback`-URL.
- **Режимы взаимоисключающие (24.11.2026):** `VpnStarter.CanStartBypass/CanStartServer` + проверки
  в `BypassActivity`, `MainActivity` (кнопки сервисов и результат разрешения VPN), `RejectedActivity`,
  `TelegramActivity`. В `TunnelService` — страховка: новый режим поверх работающего игнорируется
  с записью в журнал. Плитка быстрых настроек и автозапуск (`StartPreferred`) поднимают
  **последний** режим (обход или сервер), а не всегда сервер.
- **Страница YouTube:** в целевые домены добавлены `youtubei.googleapis.com`,
  `youtube.googleapis.com`, `gstatic.com`, `googleusercontent.com`, а видео-хосты (`i.ytimg.com`,
  `yt3.ggpht.com`) теперь тоже фрагментируются (раньше проходили напрямую). После этого страница
  догружается: рекомендации/аватары идут (`yt3.ggpht.com` 9,7 КБ), видео качается
  (`rr3---sn-…googlevideo.com` — 759 096 байт). Если приложение YouTube было подключено
  к прокси-серверу, TUN-обход не работает — сначала «Отключить» на главном экране.
- **Автоподбор (24.11.2026):** одна кнопка «Подобрать всё» — сначала все стратегии по доменам
  страницы (`www.youtube.com`, `youtubei.googleapis.com`, `i.ytimg.com`), сохраняет рабочую,
  затем по доменам видео (`redirector.googlevideo.com`, `yt3.ggpht.com`, `rr2/rr3---…googlevideo.com`),
  сохраняет видео-стратегию (если видео не нашлось — берётся стратегия страницы), и сразу включает
  обход. Домены проверяются как у приложения, не как у браузера; для API/превью успех — любой
  HTTP-ответ (<500). После включения обхода служба через 10 с проверяет страницу через свой
  форвардер: если не открылась — **сама** запускает подбор (страница, затем видео), сохраняет
  в пресет сети и перезапускает обход (кулдаун 15 мин). Замер 24.11.2026: по доменам приложения
  лучшей оказалась «Перестановка (TTL 1)» 2/4, а не OOB — поэтому автоподбор обязателен.
- **Пресеты по сети (24.11.2026):** `TunBypassStrategyWifi/Mobile` и
  `TunBypassVideoStrategyWifi/Mobile` + `NetworkPresets` (определяет Wi-Fi/мобильную по
  `ConnectivityManager`). Экран «TUN-обход» показывает текущий пресет, автоподбор сохраняет

## Улучшение сбора серверов (24.11.2026, локально, версия не поднималась)

Четыре правки в сборе бесплатных источников (P0), проверены на ПК:

- **Каналы Telegram — теперь и серверы.** `SourceKinds.IsServerSource` включает t.me-каналы
  в `CollectAsync` (раньше они были только MTProto). Сайты `SourceKind.MtProto` — по-прежнему
  только прокси. У канала нет даты на GitHub, поэтому `GitHubSourceFreshness.CheckAsync`
  пропускает его (не удаляет). При заблокированном t.me канал в сборе серверов падает с
  подсказкой, не роняя остальные.
- **Кэш дат публикации на диске** — `freshness.json` (`GitHubSourceFreshness.PersistCache`),
  чтобы после перезапуска не жечь квоту GitHub API заново.
- **Условные GET + кэш сырого ответа** — `raw-etags.json` + `rawcache/`. Источник возвращает
  ETag; при 304 список пересобирается из кэша без скачивания, поэтому серверы источника не
  пропадают из `ReplaceNodes`. Текст > 4 МБ не кэшируется.
- **Зеркала для raw-контента** — `FetchRawAsync` после прокси/прямого пробует

- **Разбор `tuic://`** — `LinkParser.ParseTuic` (TUIC v5, sing-box). `ssr://` не добавляем:
  sing-box не умеет ShadowsocksR.
- **Ротация «бесплодных» источников** (след. пункт P1) — `NodeSourceStats.RotateBarrenSources`:
  серверный источник (не мой, не MTProto) с ≥200 серверов и нулём рабочих отключается через

  из `CollectAsync` в `SourcesToDisable`/`SourcesToRemove`; применяют `RefreshSourcesCoreAsync`
  (ПК) и `NodeStore.RefreshAsync` (Android).
- **Контент-дедуп источников** (след. пункт P1) — `FetchOutcome.ContentHash` (SHA-256 текста)

## ИСПРАВЛЕНО: YouTube/трафик не шёл в VPN на телефоне/планшете (24.11.2026, 1.3.43+)

- **Симптом:** после перехода на Java-платформу (1.3.36+) телефон и планшет подключались,
  показывали выход через сервер, но трафик приложений в туннель не попадал: Chrome/YouTube
  висели, `tun0` почти не рос, в логе ядра только `inbound DNS packet` (без TCP).
- **Причина:** в `VieNLink.Android/Java/VieNLinkJavaBridge.java`, метод `openTun`, счётчик
  добавленных маршрутов считал и **адреса** (`Inet4Address` = 172.19.0.1/30), поэтому
  fallback `addRoute("0.0.0.0", 0)` не срабатывал при пустом `Inet4RouteAddress` (так
  `auto_route: true` и ведёт себя). В VPN-таблице был только собственный подсет
  `172.19.0.0/30` — DNS доходил (на 172.19.0.1), а TCP шёл напрямую.
- **Исправление:** счётчик теперь считает только маршруты (как в C#-платформе `TunnelService.OpenTun`).
- **Проверено:** `dotnet build` — 0 ошибок; собран и установлен на телефон
  (`release\VieNLink-1.3.43-phone.apk`): в VPN-таблице появился `default dev tun0`,
  tun0 RX 3,9 КБ → 5,6 МБ, TCP идёт `inbound/tun → outbound/vless` к YouTube.
- **Релиз 1.3.44:** версия поднята (1.3.44 / 10344), CHANGELOG обновлён, собраны все сборки
  (телефон `-phone.apk`, ТВ `-tv-arm32.apk`, магазинная `-store.apk/.aab`, Windows `setup.exe` + ZIP +
  `SHA256SUMS.txt`). Опубликовано на GitHub: `v1.3.44-beta` (Windows) и `v1.3.44-android`

## Android, Java-платформа libbox и тестовая сборка (23.11.2026, 1.3.35+)

- **Зачем:** убрать горячие вызовы ядра из MonoVM. `PlatformInterface` целиком на Java
  (`VieNLink.Android/Java`, package `com.vienlink.platform`): `VieNLinkJavaBridge`
  (один `CommandServer` на процесс, TUN, `protect`, интерфейсы, монитор сети),
  `VieNLinkJavaPlatform`, `VieNLinkServerHandler`, `VieNLinkDnsTransport`.
- **Мост C#:** `JavaBridge.cs` ищет класс через

  C# вызывает Java только `setService`/`start`/`stop`/`closeTun`/`hasTun`;
  всё остальное ядро дёргает на Java.
- **Сборка:** `-p:AndroidJavaPlatform=true`. **С 24.11.2026 Java-платформа включена
  по умолчанию во все сборки** (`TestBuild=false/true`, ТВ): на телефоне она не даёт
  зависаний MonoVM после фона, проверена на телефоне, планшете и ТВ. Параметр
  `-p:AndroidJavaPlatform=false` остаётся как аварийный откат на C#-платформу.
  `build\publish-android.ps1 -TestBuild` по-прежнему собирает отдельный package
  `com.vienlink.app.test` («VieNLink Test»), но он больше не нужен для проверки Java —
  основная сборка `com.vienlink.app` тоже на Java.
  Для Release Java-классы держит `keep-java.txt` (`-keep class com.vienlink.platform.**`).
- **Проверено на телефоне:** `JavaBridge: VpnService готов`, `CommandServer создан`,

## Android, зависание после простоя в фоне (23.11.2026, 1.3.35+)

- **Симптом:** приложение возвращается из фона пустым и не реагирует; система показывает
  ANR `Broadcast of Intent … MAINTENANCE`. На телефоне это воспроизвелось 23.11.2026
  несколько раз (19:50, 20:20, 21:06, 21:50).
- **Причина — не наш код:** в ANR-трейсе главный поток и все управляемые потоки стоят
  в `suspend_signal_handler`/`sigsuspend`, а поток остановки мира — в
  `mono_threads_wait_pending_operations`. Окно не рисуется (`reportedDrawn=false`),
  broadcast не обрабатывается. Это дедлок STW в MonoVM (.NET 10):
  dotnet/runtime#114064 (вытесняющая остановка на pthread-замке bionic) и
  #111485 (attach/GC). В `MainActivity`/`MaintenanceReceiver` его не исправить.
- **Обход:** `VieNLink.Android/Environment.txt` + `<AndroidEnvironment>` в csproj:
  - `MONO_GC_PARAMS=nursery-size=16m` — в 4 раза реже сборки (по умолчанию 4 МБ) и,
    значит, реже вызовы GC-моста, который останавливает мир;
  - `MONO_THREADS_SUSPEND=coop` — кооперативная остановка без вытесняющих сигналов
    и pthread-замков.
  В журнале при старте процесса видно `Mono: GC_PARAMS=…, THREADS_SUSPEND=…` —
  так проверяется, что файл доехал (строка в `VieNLinkApp.OnCreate`).
- **Код:** `EnsureFreshCountersAsync` теперь `async Task` с `CancellationToken`, идёт
  в `Task.Run`, ждёт 2,5 с (окно успевает нарисоваться), все `await` —
  `ConfigureAwait(false)`; `OnPause` отменяет задачу. `UpdateProbeBadge` кэширует
  текст/цвет/фон — больше не создаёт `GradientDrawable` и Java-строку каждые 3 с.
- **Проверено:** HOT-возврат из фона `am start -W` — 86/94/95/97 мс; до правки
  `am start -W` истекал по таймауту 10 с, окно оставалось пустым, `reportedDrawn=false`.
  Фоновая партия продолжается при ушедшем в фон приложении, ANR нет. Тестовый
  signed APK 1.3.35 (`versionCode` 10335) установлен на телефон; версия не поднималась,
  релиз не публиковался.
- **Наблюдать дальше:** если зависание повторится — убрать `MONO_THREADS_SUSPEND=coop`
  и оставить только `nursery-size`. Следующий надёжный шаг — реализовать
  `libbox.PlatformInterface` на Java (`protect`, `OpenTun`, `FindConnectionOwner`),
  чтобы Go-потоки не входили в managed-код и не создавали операции attach:
  это главный источник «pending operations» в этом приложении. Проверять по
  `dumpsys activity lastanr` и `dumpsys dropbox --print data_app_anr`.

## Локальные правки после 1.3.34: счётчики и сводка (23.11.2026)

- **Симптом:** на ПК в шапке щит показывал 3 рабочих, а значки сервисов — 0; на Android
  счётчики показывали серверы, а подключение отвечало «рабочий сервер не нашёлся».
  Причина: щит считал все записи со статусом `Working` (включая устаревшие и с провалом),
  значки — только проверки не старше 5 минут, выбор — тоже только свежие. Партия проверки
  занимает минуты, поэтому значки честно падали в ноль.
- **Решение:** новое правило показа `NodeAvailability.IsCountable` — `Working`, есть
  последний успех, `FailCount == 0`, результат не старше `WorkingDeadAfterMinutes` (60 мин),
  фильтр «Только мои». По нему считают щит и значки на ПК и Android; выбор для подключения
  остался на `IsUsable` (свежие 5 минут). `PickForService`/`BestVerified` (Android) и
  `FindNodeForServiceAsync` (ПК) при занятом пробном ядре возвращают сервер, который
  показывают счётчики, а не null — иначе кнопка говорила «серверов нет».
- **Android, живое обновление:** `:probe` пишет готовые результаты в `probe-live.json`
  (не чаще 2 раз в с; временный файл + `File.Move`), `ProbeClient.ApplyLiveResults`
  применяет новые записи к `NodeStore` прямо по ходу партии; итоговый `Apply` и отсев —
  как прежде. Экран «Серверы» показывает те же «доступные», что и шапка.
- **ПК, цвет:** `NodesSummaryText` («В списке: …») больше не чёрный на тёмном фоне —
  `Foreground` из темы, добавлена подсказка «рабочие / доступные / свежие».
- Проверки: `dotnet build VieNLink` — 0 ошибок, Android — 0 ошибок,
  `SelfTest statuslogic` — в порядке (добавлены проверки `IsCountable`).

## Локальные правки после 1.3.34: свой обход DPI (23.11.2026)

- **Причина «ошибочно определяет стратегию»:** автоподбор своего обхода DPI выбирал
  стратегию по странице YouTube и задержке, потому что проверка видео давала ложный
  «нет». `ProbeVideoDetailAsync` открывал новое TCP-соединение к подписанному адресу
  `videoplayback` и получал HTTP 0 / 0 байт, хотя в браузере видео шло (и наоборот —
  через несколько секунд замирало). Проверка также брала только первый видео-хост
  и считала успехом 1 КБ. Теперь: до 2 разных хостов googlevideo, успех — HTTP 200/206
  и ≥64 КБ, после трёх подряд пустых проверок видео больше не проверяется (экономия
  времени). Автоподбор останавливается сразу, как только видео подтвердилось.
- **Ручной выбор:** список стратегий снова кликабельный (раньше был только для чтения),
  рядом с «Включить обход» — кнопка **«Подобрать заново»**. Ручной выбор сохраняется
  (`AppSettings.DesyncManual`), и при следующем включении автоподбор больше не
  подменяет его сохранённым профилем. Это главный обходной путь, пока проверка видео
  на конкретном провайдере врёт.
- **QUIC-стратегия:** «Только QUIC-фейк» больше не пропускается жёстко. Она проверяется
  QUIC-рукопожатием (`ProbeQuicAsync`, `System.Net.Quic`, h3) и при успехе выбирается
  с выключенной блокировкой QUIC (`DesyncProbeResult.BlockQuic`). На проверенном
  провайдере QUIC заблокирован полностью: рукопожатие не проходит ни напрямую, ни с
  фейком при TTL 2/4/8/64/128 — эта стратегия не помогла, но код теперь универсален.
- **Скорость:** страница видео 12 с (было 25), видео-хост 8 с, HTTP-проба 6 с,
  максимум 2 хоста; перебор останавливается на первом видео; при недоступном
  googlevideo видео для остальных стратегий не проверяется.
- **Факт с ПК 23.11.2026:** видео **реально идёт** со стратегией **№2 «Фейк + multidisorder,
  TTL 64, seq настоящий»** — пользователь перемотал в середину, воспроизведение продолжилось
  с новых байтов. Браузер держит установленные TCP-соединения к `178.176.143.237` и
  `178.176.143.238` (локальные видео-узлы googlevideo), то есть движок до них трафик
  пропускает. Стратегия записана в `bypass-profiles.json` с **Quality 100, VideoOk=true**;
  автоподбор и следующий запуск выбирают именно её (`DesyncStrategy=2`).
- **Почему прямая проверка видео врёт:** `curl` и .NET `HttpClient` (Schannel) при запросе
  `videoplayback` получают 0 байт, хотя браузер играет: ТСПУ/узел пропускает браузерный
  TLS, а YouTube подписывает поток в JS (`n`/PO-токен).
- **Решение — yt-dlp:** `YtDlpVideoProbe` скачивает `yt-dlp.exe` (23 МБ) в
  `%LOCALAPPDATA%\VieNLink\yt-dlp.exe` (GitHub + зеркала `ghfast.top`, `gh-proxy.com`)
  и запускает его с `--extractor-args youtube:player_client=android -f worst[height<=360]
  --max-filesize 6M`. Android-клиент yt-dlp получает подписанный URL и качает реальные
  байты; проверено — **629 172 байта** за доли секунды. В `AutoTuneAsync` после неудачи
  curl вызывается yt-dlp; при ≥64 КБ стратегия получает `VideoOk=true`, перебор
  останавливается, профиль пишется в `bypass-profiles.json` с качеством 100.
  Сейчас там: «Фейк + multidisorder, TTL 64, seq настоящий» — Quality 100, VideoOk=true,
  поэтому автоподбор и следующий запуск выбирают именно её. Проверка yt-dlp не зависит
  от элевации (в отличие от браузерного CDP, который из админ-приложения обрывался).
- **Итог:** обход DPI (#2) рабочий, видео идёт без сервера; автоподбор теперь
  **видит видео** и запоминает рабочую стратегию у всех пользователей. «Подобрать заново»
  проверяет выбранную стратегию первой (`preferredIndex`), поэтому подтверждение занимает
  один проход, а не 15.
- **UI:** стратегии и пресеты zapret — кликабельные плашки-переключатели
  (`StrategyRadioButton`) с подсветкой выбранной; рядом кнопки «Подобрать заново»;
  все кнопки получили градиент, тень, hover/pressed/focus-состояния; вкладки —
  цветные подчёркивания и плашки (`TabItem.Tag` → цвет: подключение/серверы зелёные,
  zapret красный, свой DPI синий, TUN индиго, инструменты бирюзовые, отсев красный);
  шапка больше не дублирует название сервера (имя + отдельный адрес), карточка
  фиксированной ширины `Hidden`, а не `Collapsed`, поэтому кнопки не смещаются;
  выделение вкладок и стратегий — синее (`SelectionSurfaceBrush`), плашки стратегий
  синевато-серые; окно **фиксированного размера 980×680**: края не тянутся
  (`WM_NCHITTEST` → `HTBORDER`), «свернуть/развернуть» работают (проверено
  980×680 → 1936×1048 → 980×680), последняя позиция сохраняется (при свёрнутом —
  по `RestoreBounds`).
- **Zapret — то же самое:** `ZapretService.AutoTuneAsync` теперь тоже проверяет видео
  через `yt-dlp` (после страницы и `redirector.googlevideo.com`), пишет `VideoOk`
  в `ZapretProbeResult` и в профиль (`ZapretProfile` → Quality 100), останавливается на
  реальном видео и проверяет сохранённый пресет первым (`GetPriorityOrder(preferred)`).
  Пресеты кликабельные, есть «Подобрать заново», ручной выбор (`ZapretManual`).
- **Пропажа рабочих серверов без отсева:** причина — `NodeSourceService.LoadCache`

- Android, причина зависаний: UI ждал `NodeStore.Gate`, пока фон разбирал кэш на 12 000
  серверов (системный ANR «Input dispatching timed out» на старте и при нажатиях).
  Теперь список публикуется неизменяемым снимком (`NodeStore._snapshot`), счётчики,
  выбранный сервер и сводка читаются без замка; тяжёлая работа — только в фоне.
- Android, причина потери рабочих серверов: `:probe` — отдельный процесс, он разбирал
  ссылки в новые объекты и не знал прежний `Status`/`FailCount`, поэтому рабочий сервер
  после **одного** провала помечался мёртвым и удалялся. Теперь история едет в запросе
  (`ProbeRequestNode.Status/FailCount`), правило «2 провала подряд» работает и на Android.
  Плюс при загрузке кэша рабочий сервер с провалом (schema ≥ 3, `FailCount ≥ 1`) не
  выбрасывается как «мусор старого кэша».
- Android: рабочее и непроверенное хранятся отдельно — `nodes-working.json` (маленький,
  пишется после каждой проверки) и `nodes.json` (куча, не чаще раза в минуту/5 минут).
- Android: на запуске сначала грузятся рабочие из своего файла и сразу перепроверяются
  (`Старт: рабочие перепроверены — N, живых M`), только потом поиск новых.
- Рабочий сервер переживает один провал и сохраняет результат последней удачной проверки;
  удаляется после 2 провалов подряд, непроверенный — после первой неудачной. Счётчики в шапке считают
  по одной базе (без учёта свежести), поэтому общее число и значки сервисов сходятся
  по смыслу: сумма значков больше общего числа, т.к. один сервер открывает несколько сервисов.
- Android: в шапке отдельный значок «рабочих серверов» — число берётся из списка рабочих
  (`nodes-working.json`), туда же сразу попадают найденные при проверке; рядом
  «+прибавилось −убыло». Во время ручного прогона фоновая проверка не запускается,
  кнопка «Остановить поиск» относится только к ручному прогону.
- Рабочие серверы проверяются мягче (обе платформы): первый провал не стирает результат,
  вторая попытка в том же проходе, TCP-отсев не наказывает рабочие; удаление — после 2 провалов.
- Clash API: таймаут 10 с (было 30) и свой предел на запрос задержки — проверка не замирает.
- Windows: то же разделение через `VieNLink\NodeCacheWriter.cs`; на ПК правило
  «2 провала» работало и раньше (`HiddenProbeService` + `ProxyManager` меняют настоящие
  объекты), общий для платформ остался только фильтр загрузки кэша.
- Windows, обновление приложения: в «Общих» появились кнопка «Проверить обновление»,
  строка статуса и кнопка «Скачать и установить» → «Запустить установщик». Автопроверка
  при запуске ведёт к тем же шагам: процент скачивания виден в «Общих» и в строке
  состояния, установщик запускается обычным окном (`/CLOSEAPPLICATIONS /NORESTART`),
  а не `/SILENT`, и после установки предлагает запустить новую версию.
- Статистика источников: в списке источников ПК колонки «Всего» (уникальные серверы
  за всё время, `TotalNodeCount` + `RegisteredNodeIds`) и «Рабочих» (текущие), на Android —
  `всего: N · рабочих: M`. Повторный сбор не раздувает «Всего», старый кэш заполняет его
  при запуске (`NodeSourceStats.SeedTotals`). По нулю рабочих видно, какой источник
  можно удалить.
- Автоматика: в настройках ПК раздел «Автоматические работы» — отдельные переключатели
  автопоиска источников, авто-сбора серверов, обновления подписок при запуске, MTProto,
  ядра sing-box и обновлений приложения; проверка серверов — рядом. На Android такие же
  переключатели в «Настройках»; `AutomationPaused` по-прежнему гасит всё сразу.
- Android: нижние вкладки «Подключение / Обход / Инструменты / Настройки». Журнал —
  плитка в «Инструментах» (`LogActivity`), четвёртая вкладка открывает `SettingsActivity`
  и после возврата показывает прежнюю вкладку.
- Android: одно нажатие «Проверить серверы» — 5 партий по 200 (до 1000 серверов),
  подпись «Партия N из 5»; рабочие проверяются отдельным проходом после поиска новых.
- Android: пока идёт ручной прогон, фоновая проверка партии не запускает (`IsManualRun`),
  иначе `:probe` переходил из рук в руки и счётчик замирал.
- Android: ожидание результата `:probe` прерывается, если счётчики прогресса не меняются
  100 с (раньше «живой» файл прогресса держал ожидание все 10 минут); второй запуск
  в том же процессе `:probe` игнорируется.
- Android: «Остановить поиск» реагирует сразу (снимает состояние, принудительно гасит
  `:probe`), повторное нажатие запускает новую партию, а не «ничего».
- Android: лимит списка 5000 (схема настроек 4; старый кэш подрезается при чтении),
  партия проверки 200, `OpenedFor` без `ToLowerInvariant` (меньше мусора для GC).
- Журнал Android дублируется в logcat: `adb logcat -s VieNLinkLog`.
- Замер на телефоне (VPN включён): PSS основного процесса 351 → **~150 МБ**, холодный
  старт ~0,9 с, новых ANR нет; `:probe` — отдельный процесс ~180–220 МБ на время партии.
  APK для проверки собран как `1.3.7`/`10308`
  (`release\VieNLink-1.3.7-android.apk`) — ставится поверх, в GitHub не выкладывать.

## Грабли, проверенные на практике

- ПК нельзя автоматизировать через UI Automation: кастомный `TabItem` не отдаёт содержимое
  вкладок. Проверять через `SelfTest` (`parsers`, `checkconfigs`, `statuslogic`, `hiddenprobe`)
  и журнал `%LOCALAPPDATA%\VieNLink\logs`.
- Android Activity не экспортированы: `am start` не откроет Telegram/Nodes и т.п. — только
  запуск главного экрана и тапы по координатам (скриншот 1080×2354, координаты `input tap`
  в пикселях устройства).
- Зависания Android ищутся так: `adb shell dumpsys activity lastanr`,
  `adb shell dumpsys dropbox --print data_app_anr` (там причина и стек главного потока).
  Главный поток в `__rt_sigsuspend`/`pollOnce` — приложение было занято (или его держал GC),
  а не «мертво». Смотреть также `dumpsys meminfo` (PSS) и `ps -A` по `:probe`.
- UI-поток Android не должен трогать замки `NodeStore`: только снимок `_snapshot`
  (`Snapshot`, `Summary`, `DetailedSummary`, `Selected`). Всё тяжёлое — в `Task.Run`.
- Вывод `adb screencap` в перенаправленный файл на Windows может испортиться — снимать в
  `/sdcard`, затем `adb pull`.
- `dotnet build VieNLink.slnx` падает на Android-проекте без workload — собирать
  `VieNLink\VieNLink.csproj` и Android отдельным SDK.
- Перед сборкой закрыть `VieNLink.exe`, иначе файлы в `bin` заблокированы.
- Живых серверов в открытых списках 0,2–3 %; видео YouTube у некоторых провайдеров требует
  прокси-сервер (локальный GGC блокируется по IP).
