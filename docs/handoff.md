## Android: рабочие серверы в отсеве — правка подтверждения провала (24.11.2026)

- **Симптом:** на Android в «Отсев — Перепроверка» попадают серверы, которые реально
  открывают сайты; на ПК отсев стабилен.
- **Причина (найдена по коду):** последняя защита от ложного «мёртвого» сервера —
  `NodeTester.ConfirmOnceAsync` (подтверждение провала после партии в процессе `:probe`) —
  на Android проверяла только **Cloudflare и YouTube**, а на ПК (`ProxyManager.ConfirmOnceAsync`)
  — Cloudflare, YouTube и **Telegram**. Рабочий сервер, который после партии открыл только
  Telegram/Discord, на Android считался мёртвым, на ПК — нет.
- **Исправление:** в `VieNLink.Android/NodeTester.cs` список подтверждения расширен до
  Cloudflare + YouTube + Telegram (`t.me`, `web.telegram.org`) + Discord, а в блоке
  «подтверждён» добавлена запись `DiscordOk` (раньше флаг не обновлялся).
- **Проверено:** `dotnet build VieNLink.Android` (локальный dotnet c android workload) — 0 ошибок.
- **Открытый вопрос (наблюдать):** если ложный отсев повторится, причина может быть в DNS
  пробного ядра `:probe` (пакетная проверка использует UDP `77.88.8.8`, перепроверка отсева —
  TCP через сервер): при недоступном `77.88.8.8` на мобильной сети пакетная проверка ложно
  валит рабочие серверы. Нужны логи `probe`/`test` с устройства для подтверждения.

## Улучшение сбора серверов (24.11.2026, локально, версия не поднималась)

Четыре правки в сборе бесплатных источников (P0), проверены на ПК:

- **Каналы Telegram — теперь и серверы.** `SourceKinds.IsServerSource` включает t.me-каналы
  в `CollectAsync` (раньше они были только MTProto). Сайты `SourceKind.MtProto` — по-прежнему
  только прокси. У канала нет даты на GitHub, поэтому `GitHubSourceFreshness.CheckAsync`
  пропускает его (не удаляет). При заблокированном t.me канал в сборе серверов падает с
  подсказкой, не роняя остальные.
- **Кэш дат публикации на диске** — `freshness.json` (`GitHubSourceFreshness.PersistCache`),
  чтобы после перезапуска не жечь квоту GitHub API заново.
- **Условные GET + кэш сырого ответа** — `raw-etags.json` + `rawcache/`. Источник возвращает
  ETag; при 304 список пересобирается из кэша без скачивания, поэтому серверы источника не
  пропадают из `ReplaceNodes`. Текст > 4 МБ не кэшируется.
- **Зеркала для raw-контента** — `FetchRawAsync` после прокси/прямого пробует
  `ghfast.top`/`gh-proxy.com` для `raw.githubusercontent.com`.
- **Разбор `tuic://`** — `LinkParser.ParseTuic` (TUIC v5, sing-box). `ssr://` не добавляем:
  sing-box не умеет ShadowsocksR.
- **Ротация «бесплодных» источников** (след. пункт P1) — `NodeSourceStats.RotateBarrenSources`:
  серверный источник (не мой, не MTProto) с ≥200 серверов и нулём рабочих отключается через
  3 дня после `FirstSeenUtc` и удаляется через 7 дней карантина (`BarrenSinceUtc`).
  `FirstSeenUtc` ставится при загрузке списка (миграция без смены схемы). Решения приходят
  из `CollectAsync` в `SourcesToDisable`/`SourcesToRemove`; применяют `RefreshSourcesCoreAsync`
  (ПК) и `NodeStore.RefreshAsync` (Android).
- **Контент-дедуп источников** (след. пункт P1) — `FetchOutcome.ContentHash` (SHA-256 текста)
  и `NodeSourceStats.DedupMirrors`: источники с одинаковым текстом — зеркала; лучший остаётся,
  автоподобранные зеркала удаляются (`SourcesToRemove`), встроенные просто не дублируют узлы.
- **Telegram-каналы серверов через RSS** — `FetchAsync` разложен на `FetchTelegramAsync`
  (прямой t.me → RSS-зеркала `NodeSourceService.TelegramRssMirrors`, общие с MTProto) и
  `ParseText` (общий разбор). При заблокированном t.me конфиг-каналы дают серверы через RSS
  (проверено: `@v2rayng_config` — 1 сервер вместо нуля). Зеркала перенесены из `MtProtoService`
  в общий `NodeSourceService`, MTProto-путь не менялся.
- **Бюджет обращений к GitHub API** — `GitHubSourceFreshness.ApiBudget` (30 на сбор):
  источники сверх лимита собираются без проверки даты, а не пропускаются. `CheckAsync`
  принимает опциональный `budget`; проверено `statuslogic` (2 теста) и `seed`.
- **«Переехал ≠ умер»** — источник без определяемой даты публикации больше не удаляется
  сразу: карантин (`QuarantineSinceUtc`, отключение через `SourcesToDisable`), удаление —
  `RotateQuarantinedSources` после `QuarantineRemoveAfter` (7 дней). Дата снова появилась —
  карантин снимается. Недоступный API карантин не вызывает. Проверено `statuslogic` (3 теста).
- **Автопоиск сайтов + GitLab/Gitee** — `DiscoverWebAsync` оживлён (дата из адреса →
  `LastPublishedUtc`), `SourceLocation.Host` разбирает GitLab/Gitee raw и свежесть через их
  API; автопоиск теперь ищет и по GitLab/Gitee (поиск → дерево → файлы). `includeWeb=false`
  отключает обход сайтов на ТВ (в `Maintenance`, `MainActivity.Pages`, `SourcesActivity`).
  Windows и Android собираются, `statuslogic`/`parsers` — всё в порядке.

Проверено: `dotnet build` (Core/Win/SelfTest) — 0 ошибок; `SelfTest parsers` — всё в порядке
(добавлены тесты tuic и `IsServerSource`); `SelfTest fetch <raw-url>` — 4803 узла, повторный

## ИСПРАВЛЕНО: YouTube/трафик не шёл в VPN на телефоне/планшете (24.11.2026, 1.3.43+)

- **Симптом:** после перехода на Java-платформу (1.3.36+) телефон и планшет подключались,
  показывали выход через сервер, но трафик приложений в туннель не попадал: Chrome/YouTube
  висели, `tun0` почти не рос, в логе ядра только `inbound DNS packet` (без TCP).
- **Причина:** в `VieNLink.Android/Java/VieNLinkJavaBridge.java`, метод `openTun`, счётчик
  добавленных маршрутов считал и **адреса** (`Inet4Address` = 172.19.0.1/30), поэтому
  fallback `addRoute("0.0.0.0", 0)` не срабатывал при пустом `Inet4RouteAddress` (так
  `auto_route: true` и ведёт себя). В VPN-таблице был только собственный подсет
  `172.19.0.0/30` — DNS доходил (на 172.19.0.1), а TCP шёл напрямую.
- **Исправление:** счётчик теперь считает только маршруты (как в C#-платформе `TunnelService.OpenTun`).
- **Проверено:** `dotnet build` — 0 ошибок; собран и установлен на телефон
  (`release\VieNLink-1.3.43-phone.apk`): в VPN-таблице появился `default dev tun0`,
  tun0 RX 3,9 КБ → 5,6 МБ, TCP идёт `inbound/tun → outbound/vless` к YouTube.
- **Релиз 1.3.44:** версия поднята (1.3.44 / 10344), CHANGELOG обновлён, собраны все сборки
  (телефон `-phone.apk`, ТВ `-tv-arm32.apk`, магазинная `-store.apk/.aab`, Windows `setup.exe` + ZIP +
  `SHA256SUMS.txt`). Опубликовано на GitHub: `v1.3.44-beta` (Windows) и `v1.3.44-android`

  `-tv-arm32.apk` собран, но на ТВ не установлен (ТВ этим багом не затронут).

## Android, зависание после простоя в фоне (23.11.2026, 1.3.35+)

- **Симптом:** приложение возвращается из фона пустым и не реагирует; система показывает
  ANR `Broadcast of Intent … MAINTENANCE`. На телефоне это воспроизвелось 23.11.2026
  несколько раз (19:50, 20:20, 21:06, 21:50).
- **Причина — не наш код:** в ANR-трейсе главный поток и все управляемые потоки стоят
  в `suspend_signal_handler`/`sigsuspend`, а поток остановки мира — в
  `mono_threads_wait_pending_operations`. Окно не рисуется (`reportedDrawn=false`),
  broadcast не обрабатывается. Это дедлок STW в MonoVM (.NET 10):
  dotnet/runtime#114064 (вытесняющая остановка на pthread-замке bionic) и
  #111485 (attach/GC). В `MainActivity`/`MaintenanceReceiver` его не исправить.
- **Обход:** `VieNLink.Android/Environment.txt` + `<AndroidEnvironment>` в csproj:
  - `MONO_GC_PARAMS=nursery-size=16m` — в 4 раза реже сборки (по умолчанию 4 МБ) и,
    значит, реже вызовы GC-моста, который останавливает мир;
  - `MONO_THREADS_SUSPEND=coop` — кооперативная остановка без вытесняющих сигналов
    и pthread-замков.
  В журнале при старте процесса видно `Mono: GC_PARAMS=…, THREADS_SUSPEND=…` —
  так проверяется, что файл доехал (строка в `VieNLinkApp.OnCreate`).
- **Код:** `EnsureFreshCountersAsync` теперь `async Task` с `CancellationToken`, идёт
  в `Task.Run`, ждёт 2,5 с (окно успевает нарисоваться), все `await` —
  `ConfigureAwait(false)`; `OnPause` отменяет задачу. `UpdateProbeBadge` кэширует
  текст/цвет/фон — больше не создаёт `GradientDrawable` и Java-строку каждые 3 с.
- **Проверено:** HOT-возврат из фона `am start -W` — 86/94/95/97 мс; до правки
  `am start -W` истекал по таймауту 10 с, окно оставалось пустым, `reportedDrawn=false`.
  Фоновая партия продолжается при ушедшем в фон приложении, ANR нет. Тестовый
  signed APK 1.3.35 (`versionCode` 10335) установлен на телефон; версия не поднималась,
  релиз не публиковался.
- **Наблюдать дальше:** если зависание повторится — убрать `MONO_THREADS_SUSPEND=coop`
  и оставить только `nursery-size`. Следующий надёжный шаг — реализовать
  `libbox.PlatformInterface` на Java (`protect`, `OpenTun`, `FindConnectionOwner`),
  чтобы Go-потоки не входили в managed-код и не создавали операции attach:
  это главный источник «pending operations» в этом приложении. Проверять по
  `dumpsys activity lastanr` и `dumpsys dropbox --print data_app_anr`.

## Локальные правки после 1.3.34: счётчики и сводка (23.11.2026)

- **Симптом:** на ПК в шапке щит показывал 3 рабочих, а значки сервисов — 0; на Android
  счётчики показывали серверы, а подключение отвечало «рабочий сервер не нашёлся».
  Причина: щит считал все записи со статусом `Working` (включая устаревшие и с провалом),
  значки — только проверки не старше 5 минут, выбор — тоже только свежие. Партия проверки
  занимает минуты, поэтому значки честно падали в ноль.
- **Решение:** новое правило показа `NodeAvailability.IsCountable` — `Working`, есть
  последний успех, `FailCount == 0`, результат не старше `WorkingDeadAfterMinutes` (60 мин),
  фильтр «Только мои». По нему считают щит и значки на ПК и Android; выбор для подключения
  остался на `IsUsable` (свежие 5 минут). `PickForService`/`BestVerified` (Android) и
  `FindNodeForServiceAsync` (ПК) при занятом пробном ядре возвращают сервер, который
  показывают счётчики, а не null — иначе кнопка говорила «серверов нет».
- **Android, живое обновление:** `:probe` пишет готовые результаты в `probe-live.json`
  (не чаще 2 раз в с; временный файл + `File.Move`), `ProbeClient.ApplyLiveResults`
  применяет новые записи к `NodeStore` прямо по ходу партии; итоговый `Apply` и отсев —
  как прежде. Экран «Серверы» показывает те же «доступные», что и шапка.
- **ПК, цвет:** `NodesSummaryText` («В списке: …») больше не чёрный на тёмном фоне —
  `Foreground` из темы, добавлена подсказка «рабочие / доступные / свежие».
- Проверки: `dotnet build VieNLink` — 0 ошибок, Android — 0 ошибок,
  `SelfTest statuslogic` — в порядке (добавлены проверки `IsCountable`).

## Локальные правки после 1.3.34: свой обход DPI (23.11.2026)

- **Причина «ошибочно определяет стратегию»:** автоподбор своего обхода DPI выбирал
  стратегию по странице YouTube и задержке, потому что проверка видео давала ложный
  «нет». `ProbeVideoDetailAsync` открывал новое TCP-соединение к подписанному адресу
  `videoplayback` и получал HTTP 0 / 0 байт, хотя в браузере видео шло (и наоборот —
  через несколько секунд замирало). Проверка также брала только первый видео-хост
  и считала успехом 1 КБ. Теперь: до 2 разных хостов googlevideo, успех — HTTP 200/206
  и ≥64 КБ, после трёх подряд пустых проверок видео больше не проверяется (экономия
  времени). Автоподбор останавливается сразу, как только видео подтвердилось.
- **Ручной выбор:** список стратегий снова кликабельный (раньше был только для чтения),
  рядом с «Включить обход» — кнопка **«Подобрать заново»**. Ручной выбор сохраняется
  (`AppSettings.DesyncManual`), и при следующем включении автоподбор больше не
  подменяет его сохранённым профилем. Это главный обходной путь, пока проверка видео
  на конкретном провайдере врёт.
- **QUIC-стратегия:** «Только QUIC-фейк» больше не пропускается жёстко. Она проверяется
  QUIC-рукопожатием (`ProbeQuicAsync`, `System.Net.Quic`, h3) и при успехе выбирается
  с выключенной блокировкой QUIC (`DesyncProbeResult.BlockQuic`). На проверенном
  провайдере QUIC заблокирован полностью: рукопожатие не проходит ни напрямую, ни с
  фейком при TTL 2/4/8/64/128 — эта стратегия не помогла, но код теперь универсален.
- **Скорость:** страница видео 12 с (было 25), видео-хост 8 с, HTTP-проба 6 с,
  максимум 2 хоста; перебор останавливается на первом видео; при недоступном
  googlevideo видео для остальных стратегий не проверяется.
- **Факт с ПК 23.11.2026:** видео **реально идёт** со стратегией **№2 «Фейк + multidisorder,
  TTL 64, seq настоящий»** — пользователь перемотал в середину, воспроизведение продолжилось
  с новых байтов. Браузер держит установленные TCP-соединения к `178.176.143.237` и
  `178.176.143.238` (локальные видео-узлы googlevideo), то есть движок до них трафик
  пропускает. Стратегия записана в `bypass-profiles.json` с **Quality 100, VideoOk=true**;
  автоподбор и следующий запуск выбирают именно её (`DesyncStrategy=2`).
- **Почему прямая проверка видео врёт:** `curl` и .NET `HttpClient` (Schannel) при запросе
  `videoplayback` получают 0 байт, хотя браузер играет: ТСПУ/узел пропускает браузерный
  TLS, а YouTube подписывает поток в JS (`n`/PO-токен).
- **Решение — yt-dlp:** `YtDlpVideoProbe` скачивает `yt-dlp.exe` (23 МБ) в
  `%LOCALAPPDATA%\VieNLink\yt-dlp.exe` (GitHub + зеркала `ghfast.top`, `gh-proxy.com`)
  и запускает его с `--extractor-args youtube:player_client=android -f worst[height<=360]
  --max-filesize 6M`. Android-клиент yt-dlp получает подписанный URL и качает реальные
  байты; проверено — **629 172 байта** за доли секунды. В `AutoTuneAsync` после неудачи
  curl вызывается yt-dlp; при ≥64 КБ стратегия получает `VideoOk=true`, перебор
  останавливается, профиль пишется в `bypass-profiles.json` с качеством 100.
  Сейчас там: «Фейк + multidisorder, TTL 64, seq настоящий» — Quality 100, VideoOk=true,
  поэтому автоподбор и следующий запуск выбирают именно её. Проверка yt-dlp не зависит
  от элевации (в отличие от браузерного CDP, который из админ-приложения обрывался).
- **Итог:** обход DPI (#2) рабочий, видео идёт без сервера; автоподбор теперь
  **видит видео** и запоминает рабочую стратегию у всех пользователей. «Подобрать заново»

**Локальные правки, вошедшие в 1.3.24 (23.11.2026):**
- ПК: счётчики в шапке обновляются каждые 3 секунды (было раз в минуту); строка стала

  рядом со значками сервисов (как на Android), текст «Серверы: N» остался рядом.

  партии («ни один сервер не открылся») статусы восстанавливались, но сервер уже был записан
  в отсев. Исправлено: подключение только переключает сервер, статус меняет лишь скрытая
  проверка; отсев пополняется после завершения партии (`RepartitionAndSaveAsync`), после

  удаляются из `nodes-rejected.json`; сервер, через который идёт трафик, скрытая проверка
  не отсеивает (ПК — `_manager.CurrentNode`, Android — `NodeStore.Selected`); успешное
  подключение из отсева возвращает сервер в рабочие автоматически. Перепроверка без
  подключения — по-прежнему «Вернуть» вручную. На ПК в отсеве колонка «Состояние»

  «ПРОВЕРКА ПРОШЛА».
- Проверка непроверенных (Android): после TCP-отсева нерабочие непроверенные серверы теперь
  сразу удаляются (`NodeStore.DropDeadNodes`, в журнале «Убрано нерабочих серверов: N»),
  а не остаются в кэше мёртвыми до перезагрузки. Битая ссылка с одиночным «%» в пути ws
  больше не валит запуск всей партии (`LinkParser`).

  проверки вырастут, пока квота не набрана.
- Источники: удалены `V2RayAggregator`, `ShadowsocksAggregator`, `get_subscribe`,

## Грабли, проверенные на практике

- ПК нельзя автоматизировать через UI Automation: кастомный `TabItem` не отдаёт содержимое
  вкладок. Проверять через `SelfTest` (`parsers`, `checkconfigs`, `statuslogic`, `hiddenprobe`)
  и журнал `%LOCALAPPDATA%\VieNLink\logs`.
- Android Activity не экспортированы: `am start` не откроет Telegram/Nodes и т.п. — только
  запуск главного экрана и тапы по координатам (скриншот 1080×2354, координаты `input tap`
  в пикселях устройства).
- Зависания Android ищутся так: `adb shell dumpsys activity lastanr`,
  `adb shell dumpsys dropbox --print data_app_anr` (там причина и стек главного потока).
  Главный поток в `__rt_sigsuspend`/`pollOnce` — приложение было занято (или его держал GC),
  а не «мертво». Смотреть также `dumpsys meminfo` (PSS) и `ps -A` по `:probe`.
- UI-поток Android не должен трогать замки `NodeStore`: только снимок `_snapshot`
  (`Snapshot`, `Summary`, `DetailedSummary`, `Selected`). Всё тяжёлое — в `Task.Run`.
- Вывод `adb screencap` в перенаправленный файл на Windows может испортиться — снимать в
  `/sdcard`, затем `adb pull`.
- `dotnet build VieNLink.slnx` падает на Android-проекте без workload — собирать
  `VieNLink\VieNLink.csproj` и Android отдельным SDK.
- Перед сборкой закрыть `VieNLink.exe`, иначе файлы в `bin` заблокированы.
- Живых серверов в открытых списках 0,2–3 %; видео YouTube у некоторых провайдеров требует
  прокси-сервер (локальный GGC блокируется по IP).
